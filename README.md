# Tmax Pro*C Service Manager

Windows용 로컬 서비스 정의·SQL 관리 도구입니다. 업무 테이블 사전·Excel 등록, SQL/두 테이블 JOIN, Tmax 전문 동기화 및 조회용 Pro*C 생성까지 지원합니다. 실제 Oracle 연결 없이 동작하며 SQL을 실행하지 않습니다.

## 3·4단계 사용 흐름

1. 서비스/테이블을 선택하고 SQL을 생성합니다. 두 테이블 JOIN 및 직접 SQL 편집도 유지합니다.
2. ‘Tmax 전문 매핑’에서 GET/PUT을 분리해 확인하고 변수명·호스트 타입/길이·전문 순서를 수정합니다.
3. SQL을 직접 수정했다면 ‘최종 SQL 분석 / 동기화 미리보기’에서 신규/변경/삭제 후보와 자료형을 확인한 후 반영합니다. 수동 이름과 전문 순서는 기본 보존합니다. SQL에서 빠진 매핑은 기본 보관하며, Pro*C 생성 전에는 명시적으로 정리해야 합니다.
4. 계산식의 타입이 미확정이면 DB/결과 자료형·정밀도/스케일·길이를 확인합니다. 출력 순서를 SELECT대로 맞추는 작업은 별도 체크로만 적용합니다.
5. 서비스를 저장한 뒤 ‘Pro*C 생성’에서 MAXROWCNT, 파일명, 인코딩을 설정하고 미리보기를 생성합니다.
6. 오류가 없으면 소스를 복사하거나 ‘생성 결과 저장’ / ‘.pc 다운로드’를 사용합니다. 같은 파일명은 확인 후 새 이력으로 보관됩니다.

기존 서비스는 마이그레이션 후 전문 동기화를 한 번 확인해 주세요. Pro*C 생성은 최종 SQL과 매핑의 연결이 검증되어야 가능합니다. 기본 파일명은 서비스 ID 소문자 `.pc`이며, MAXROWCNT는 배열 용량으로만 사용하고 SQL에 ROWNUM을 삽입하지 않습니다.

조회 템플릿은 샘플에서 확인한 asciz 타입과 매크로 서명만 사용합니다. 숫자 이름 i/d를 native int/double로 선언하지 않습니다. NULL/잘림 지시 배열은 공식 Oracle 규칙을 적용한 확장입니다. global.h/oravar/FML 정의와 실제 컴파일은 미검증입니다. GET/PUT 내부 오류 분류는 헤더 확인 전 구현하지 않았습니다.

상세 구현·테스트·제한: [3단계 보고서](STEP3_TEST_REPORT.md), [4단계 보고서](STEP4_TEST_REPORT.md), [매핑 데이터 계약](docs/MAPPING_CONTRACT.md).

## 실행

1. `start.bat`을 실행합니다.
2. 브라우저에서 http://127.0.0.1:8765 를 엽니다.
3. 실행 창에서 Ctrl+C로 종료합니다.

현재 PC의 `.venv`에 Python 3.12와 의존성을 설치했습니다. 다른 PC에는 Python 3.11 이상이 필요합니다. 최초 설치 또는 Excel 라이브러리가 없는 기존 환경의 첫 실행 시 pip 다운로드가 필요합니다. 실행 스크립트는 필요한 패키지가 설치되어 있으면 네트워크 설치를 건너뜁니다. 앱 자체는 외부 CDN/원격 API/추적/자동 업데이트를 사용하지 않습니다. 오프라인 설치는 wheel을 미리 준비하세요.

```powershell
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe run.py
```

127.0.0.1:8765 바인딩은 `run.py`에 고정되어 있습니다. Host/Origin 검사 및 변경 API의 CSRF 토큰을 적용합니다.

## 업무 테이블 사전 / Excel 사용

1. ‘업무 테이블 사전 / Excel’ 탭에서 `MDMEDORT.xlsx`를 선택하고 ‘Excel 검증 / 변경 미리보기’를 누릅니다.
2. 테이블별 전체 컬럼, 오류/경고, 신규·변경·삭제 및 영향받을 서비스를 확인합니다. 오류가 있으면 등록할 수 없습니다.
3. 반영할 항목을 체크하고 ‘선택 항목 사전에 등록’을 누릅니다. 기존 테이블의 설명 변경, 컬럼 추가/변경/삭제를 각각 선택할 수 있습니다. 미체크 항목과 파일에 없는 다른 테이블은 유지합니다.
4. 테이블명·한글 설명·컬럼명·컬럼 설명으로 검색하고 테이블을 선택합니다. 테이블 변경 이력과 사용 서비스·컬럼을 볼 수 있습니다. ‘업로드 이력’은 검증 실패/미반영/반영 상태와 파일 해시 및 반영 선택을 표시합니다.
5. ‘이 테이블을 서비스 / SQL 편집기로 가져오기’를 누릅니다. 테이블/컬럼 정의만 명시적으로 교체하며 기존 SQL과 수동 매핑은 보존합니다. 저장된 서비스에는 별도 스냅샷이 있으므로 사전 변경이 서비스를 자동 변경하지 않습니다.
6. 사전 등록 없이 수동 컬럼을 입력하는 기존 기능도 유지합니다. 수동 작성한 테이블은 ‘수동 작성한 테이블 등록’ → ‘수동 작성 컬럼으로 등록 미리보기’으로 같은 검증/비교 절차를 거쳐 재사용할 수 있습니다.

지원 헤더:

```text
TABLE_NAME, COMMENTS, TABLESPACE_NAME, COLUMN_ID, COLUMN_NAME,
DATA_TYPE, KEY, NOTNULL, DATA_DEFAULT, COMMENTS_1
```

여러 테이블/시트와 빈 시트를 처리합니다. 헤더는 각 데이터 시트의 첫 행에 있어야 합니다. 빈 TABLE_NAME은 해당 시트의 직전 테이블로 해석하므로 반복 테이블명 또는 세로 병합 형식을 사용할 수 있습니다. COLUMN_ID는 양의 정수이며 동일 테이블 내 중복 컬럼명/순서는 오류입니다. 헤더에 OWNER가 없으므로 Excel 등록의 소유자는 빈 값입니다.

PK, NOT NULL, 기본값, 원문 자료형, 길이, 정밀도, 스케일, 컬럼 설명을 보존합니다. NUMBER(p)는 scale=0, bare NUMBER는 정밀도/스케일 확인 필요로 처리합니다. PK는 NOT NULL로 취급합니다. KEY는 PK/P/PRIMARY KEY를 지원하며 FK/UK 등 알 수 없는 표기는 오류로 표시합니다. 수식 셀은 실행·추정하지 않고 값으로 변환하도록 오류 표시합니다. 기본값은 텍스트로 보관하며 실행하지 않습니다. 최대 파일 10MB, 압축 해제 합계 50MB, 20,000개 데이터 행을 허용합니다.

## SQL / Tmax 전문 구성

- 서비스 ID/설명/테이블 별칭 등을 입력합니다. 사전의 188개 컬럼을 모두 전문으로 내보낼 필요는 없습니다. 필요한 SQL 대상 컬럼을 선택하세요.
- SQL 탭의 컬럼 버튼으로 SELECT/SET 대상, WHERE, ORDER BY를 추가합니다. 컬럼을 해당 영역에 드래그하는 방법도 지원합니다. SELECT 대상 순서는 위/아래 버튼으로 변경합니다. ORDER BY 목록은 쉼표 입력으로 직접 조정할 수 있습니다.
- WHERE의 연산자 및 AND/OR를 지정합니다. WHERE가 비어 있을 때 UPDATE/DELETE로 전환하면 PK 컬럼을 기본 조건 후보로 추가합니다.
- 자동 생성 시 필요한 입력/출력 매핑만 추가합니다. 기존 수동 변수명·전문 순서와 사용하지 않는 매핑도 보존하므로 최종 GET/PUT 순서를 매핑 탭에서 검토하세요. SELECT 컬럼 순서와 기존 전문 순서를 강제로 동기화하지 않습니다.
- GET은 S_TYPE1~10, PUT은 S_STRING1~100으로 매핑 표시 순서대로 배정하며 초과 생성은 차단합니다. 매핑 순서 변경 시 전문 재배정 미리보기와 확인을 제공합니다.
- 변수 접두어는 s/i/d 이름 관례이며 실제 선언 자료형과 독립적입니다. 자동 매핑은 문자열 asciz로 정의합니다. NUMBER는 정밀도/스케일과 호스트 길이를 검사하고 문자열 입력을 TO_NUMBER로 변환합니다. DATE/TIMESTAMP는 지정 포맷의 TO_DATE/TO_TIMESTAMP 입력 및 TO_CHAR 출력을 생성하며 호스트 길이/형식을 검사합니다. 지원 포맷 토큰은 YYYY/RRRR/YY/RR/MM/MON/MONTH/DD/DDD/HH24/HH12/HH/MI/SS/AM/PM/FF1~9 및 구분자입니다. 고정된 Oracle NLS 환경은 아직 확인하지 않았으므로 숫자 소수점과 날짜 언어 포맷은 운영 환경 검증이 필요합니다.
- nullable 컬럼에 NULL 지시 변수가 없으면 경고합니다. 숫자 int/long 호스트의 정밀도 초과도 차단합니다. 사용자 정의 선언/정밀도 및 실제 asciz 정의의 컴파일 호환성은 운영 Pro*C 환경에서 검증해야 합니다.
- 바인드 변수로 CRUD SQL을 생성하며 조건 없는 UPDATE/DELETE는 위험 확인 전 차단합니다. 직접 편집 SQL은 실행하지 않으며 정적 의미 검증을 보장하지 않습니다.
- generated_sql / final_sql을 별도 보관합니다. 수동 편집본을 재생성할 때는 확인 후 기존 편집본을 저장 버전으로 보관합니다. SQL 대상/WHERE/ORDER BY 및 별칭도 서비스와 함께 저장·재열기 됩니다. UTF-8 SQL 다운로드/복사를 지원합니다.
- 서비스 신규/검색/유형 필터/복제/삭제 확인과 기존 수동 컬럼·매핑 편집을 유지했습니다.

## 데이터 및 모듈

SQLite: `data/service_manager.sqlite3`. 기존 서비스/SQL/변수/전문은 원자적으로 저장하고 서비스 버전 스냅샷·감사 로그를 남깁니다. 중복 ID/변수명과 오래된 서비스 버전 저장을 차단합니다.

시작 시 스키마 v1→v2→v3→v4 마이그레이션을 적용합니다. v3는 변수 메타데이터를, v4는 생성 결과 이력 테이블을 추가하며 기존 이름·SQL·전문 순서 및 버전 이력을 보존합니다. 기존 테이블을 삭제·재생성하지 않고 business_tables / dictionary_history / excel_imports 테이블을 추가합니다. 테이블 메타데이터와 전후 구조는 JSON 스냅샷으로 보존합니다. 사전 반영은 BEGIN IMMEDIATE 트랜잭션으로 처리하며 미리보기 기준 revision이 바뀌면 재미리보기를 요구합니다. 여러 테이블 반영 중 하나라도 실패하면 전체 반영과 이력을 롤백합니다.

- `app/services/excel_importer.py`: XLSX 읽기/유형 정규화/유효성 검사
- `app/services/table_dictionary.py`: 사전/차이/선택 반영/이력/사용 서비스 분석
- `app/services/host_validation.py`: DATE/NUMBER 호스트 검증 및 매핑 추가
- `app/dictionary_api.py`: 모듈 API
- `app/static/dictionary.js`: 사전 화면/업로드/SQL 컬럼 선택/드래그

추가 API: GET /api/dictionary/tables?q=, GET /api/dictionary/tables/{name}, GET .../{name}/usage, GET .../{name}/history, GET /api/dictionary/imports, POST /api/dictionary/excel/preview (XLSX 바이너리), POST /api/dictionary/preview (수동 정의), POST /api/dictionary/commit (미리보기 ID 및 선택 key), POST /api/sql/prepare. Oracle 임의 SQL 실행 API는 없습니다.

## 범위 및 미검증

SQL 생성은 단일 SQL 블록을 지원합니다. SELECT는 메인 테이블과 선택적인 조인 테이블 1개(총 2개)를 화면에서 구성할 수 있습니다. INSERT/UPDATE/DELETE 자동 생성은 단일 테이블용이며 JOIN이 있으면 차단합니다. 3개 이상 테이블, 식을 포함한 JOIN, 복잡한 서브쿼리는 직접 SQL로 편집합니다. 각 테이블 스냅샷은 최대 200개 컬럼을 보관합니다. 서비스 사용 컬럼은 SQL 구성의 대상·조건·정렬 및 전문 매핑을 기준으로 표시합니다. 이전 서비스에 구성 정보가 없으면 보관 컬럼 전체를 후보로 표시합니다. 수동 편집 SQL이 있는 서비스의 영향 분석은 보관 컬럼 전체까지 포함하여 보수적으로 표시합니다. 수동 SQL에 추가된 다른 테이블/서브쿼리의 의존성을 완전 분석하지 않으므로 화면에도 수동 확인 필요를 표시합니다.

Oracle 연결, 다중 SQL/PLSQL 동기화, 트랜잭션용 Pro*C·Delphi 코드 생성, 레거시 PC 불러오기, 서비스 버전 비교·복원 UI, DB 백업·복원 UI는 후속 범위입니다. 단일 SQL 토큰 분석과 조회용 Pro*C 미리보기/저장/UTF-8·CP949 다운로드는 구현했습니다. 서비스 목록의 날짜 범위 필터도 미구현입니다. 테이블 사전 변경 이력은 이번 구현에 포함됩니다.

**검증 전 운영 배포 불가.** Tmax/Oracle Pro*C 컴파일·등록·배포를 수행하지 않았습니다. 원본 PC 파일을 수정하지 않았습니다. 참고 소스 분석은 `docs/reference-analysis.md`, 확인한 헤더·매크로 의존성은 `app/templates/environment.json`에 기록했습니다.

Excel 등록 화면 수정: 수동 등록과 Excel 등록 버튼을 분리했습니다. Excel 등록 버튼은 미리보기 위/아래에 표시하며, 수동 컬럼이 비어 있을 때는 요청을 보내지 않고 한글로 안내합니다. 변경 상세를 열어도 선택 체크가 바뀌지 않으며, 선택 항목이 없으면 반영을 차단합니다. 이 흐름은 실제 Excel을 사용하는 Chrome 통합 검사에 포함됩니다.
동일 Excel 재업로드 안내 수정: 변경 사항이 0건이면 ‘이미 등록된 동일한 내용’으로 안내하고 등록 버튼을 비활성화합니다. 변경/선택 건수를 표시하고 선택 0건일 때 등록을 비활성화합니다. 실제 Excel 최초 등록 및 동일 파일 재업로드를 Chrome 통합 검사로 확인했습니다.


SQL 미리보기 수정: 서비스 ID가 비어 있어도 SQL 구성 및 전문 자동 생성은 가능합니다. 서비스 저장 시에는 ID가 필요합니다. SQL 생성 중 버튼을 비활성화하고 결과/오류를 버튼 아래에 표시하며, 성공하면 최종 SQL로 이동합니다. 경고는 별도 접이식 영역에 표시합니다. 실제 Excel을 가져온 직후 ID 입력 없이 SQL을 생성하는 Chrome 회귀 검사를 추가했습니다.
SQL 편집 화면 배치: 데스크톱에서 좌우 1:1로 분할합니다. 왼쪽 컬럼 목록은 화면 높이를 활용하고 독립 스크롤·검색·간결한 행으로 표시합니다. 오른쪽은 선택 대상/조건/정렬, SQL 생성 버튼, 최종 쿼리 편집기를 배치하며 자동 생성 원본은 접어서 볼 수 있습니다. 좁은 화면은 위아래 배치로 전환합니다. Chrome에서 두 영역의 좌우 배치, 컬럼 독립 스크롤, 생성 버튼과 쿼리 노출, 드래그/생성/저장·재열기 및 1366×768/좁은 화면을 확인했습니다.
업무 테이블 사전 배치: 등록된 테이블 목록을 오른쪽의 세로 패널로 옮기고 화면 높이를 활용하도록 했습니다. 왼쪽 업로드/미리보기/상세와 오른쪽 목록은 독립적으로 스크롤됩니다. 검색 건수도 목록 상단에 표시합니다. Chrome에서 좌우 배치와 독립 스크롤 및 기존 등록·SQL 가져오기 흐름을 확인했습니다.
테이블 사전 3영역 배치: 왼쪽 등록·미리보기, 중앙 검색·한 줄 테이블 목록, 오른쪽 선택 테이블 상세·편집기로 가져오기·변경 이력으로 구성했습니다. 각 영역을 독립 스크롤하며 선택한 목록 행을 강조합니다. Chrome에서 3영역 위치, 상세 조회·이력·편집기로 가져오기와 기존 Excel/SQL 흐름을 확인했습니다.

## 두 테이블 JOIN 사용

SQL 생성/편집 화면 왼쪽에서 다음 순서로 설정합니다.

1. ‘메인 테이블’을 사전에서 선택합니다. 수동으로 등록한 현재 테이블 정의도 그대로 사용할 수 있습니다.
2. ‘조인 테이블’을 선택하고 메인/조인 별칭을 지정합니다. 기본 별칭은 a/b이며 서로 달라야 합니다. 자기 자신을 다시 선택하는 self join도 가능합니다.
3. INNER / LEFT / RIGHT / FULL JOIN을 고르고 메인 컬럼·연산자·조인 컬럼을 지정합니다. 동일 이름 컬럼이 있으면 후보를 제안하지만 실제 업무 관계를 검토해야 합니다. 여러 ON 조건은 AND로 연결합니다(최대 10개).
4. ‘전체 / 메인 / 조인’ 컬럼 표시 필터와 검색을 이용해 양쪽 컬럼을 SELECT·WHERE·ORDER BY에 추가합니다. 컬럼은 a.PATNO / b.PATNO처럼 구분됩니다.
5. SQL 자동 생성을 누릅니다. JOIN의 ON 컬럼끼리 비교하는 조건에는 GET 전문을 만들지 않습니다. WHERE 바인드는 자동 입력 매핑으로, SELECT 대상은 출력 매핑으로 추가됩니다. 입력 10개/출력 100개 제한은 두 테이블 합계에 적용됩니다.
6. 서비스로 저장하면 테이블별 메타데이터 스냅샷, JOIN 방식/조건/별칭, 컬럼 선택, SQL, 전문 매핑이 함께 보존됩니다.

출력 SQL 별칭은 a_PATNO / b_PATNO로 구분해 중복 이름이 있는 결과도 바깥 SELECT에서 충돌하지 않게 합니다. 조인 테이블 호스트 변수는 sB_patno 같은 별칭 접두어를 사용하며 수동 변경할 수 있습니다. 별칭 변경 시 컬럼/조건/매핑의 참조를 함께 바꾸고 변수명 및 기존 SQL은 유지하므로 SQL을 다시 생성하세요. 조인 테이블 교체·해제도 기존 수동 전문 매핑을 삭제하지 않습니다. 사용하지 않는 보관 매핑은 경고를 확인하고 직접 정리하세요.

ON 조건 누락/미등록 컬럼/중복 별칭/서로 다른 자료형 계열(문자·숫자·날짜)의 비교를 차단합니다. 외부 JOIN에서 NULL이 될 수 있는 쪽의 컬럼은 원래 PK라도 nullable로 판단해 NULL 지시 변수 경고를 표시합니다. 외부 JOIN의 반대편 컬럼을 WHERE로 제한하면 INNER JOIN처럼 결과가 좁아질 수 있으므로 업무 의도를 검토하세요. 실제 Oracle 실행/Pro*C 컴파일은 미검증입니다.

테이블 사전 영향 분석은 조인 테이블 및 ON 조건에서 사용하는 컬럼도 포함합니다. SQLite의 기존 service_tables 구조와 서비스 JSON 스냅샷을 확장해 사용하므로 테이블 파괴나 데이터 변환 마이그레이션은 필요하지 않습니다. 기존 스냅샷에는 join_tables가 없으면 빈 배열로 해석합니다.

모듈: app/services/sql_sources.py(컬럼 출처·JOIN 검증), app/static/join_builder.js(테이블/JOIN 선택). JOIN 관련 19개와 후속 3·4단계 검사를 포함해 현재 전체 239개 테스트가 통과했습니다. 실제 MDMEDORT.xlsx 메타데이터와 별도의 테스트 환자 테이블을 사용해 네 JOIN 방식, 양쪽 전문, 동일 컬럼명, 다중 조건, 오류 차단, 저장/재열기, 수동 매핑 보존 및 조인 테이블 영향 분석을 검증했습니다. Chrome에서 테이블 선택 → JOIN 조건 → 양쪽 컬럼/조건/정렬 → 생성 → 저장/재열기 → 별칭 변경 → 조인 해제 흐름을 확인했습니다. 테스트 환자 테이블은 임시 DB에만 생성하며 실제 사전에는 추가하지 않습니다.

자동 생성 SELECT에는 ROWNUM 제한이나 이를 위한 바깥 SELECT 래퍼를 추가하지 않습니다. 기본정보의 최대 조회 건수 값은 정의에 보관되지만 SQL 생성에는 사용하지 않습니다. 기존 저장/편집 SQL은 자동 변경하지 않으며 재생성 시 새 형식을 적용합니다.
